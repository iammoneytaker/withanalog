# WithAnalog 키보드 테스트·비교 플랫폼 계획

작성: 2026-09-08. 상태: 제품 방향 및 실행 계획 제안. 구현·배포는 수행하지 않음.

## 목표와 보호 범위

키보드를 직접 확인하고, 근거가 있는 제품 성능을 비교하고, 마니아가 데이터 개선에 참여하는 한국어 플랫폼을 만든다. 검색 유입 → 테스트/가이드 → 제품 상세 → 비교 → 근거 확인의 흐름을 연결한다.

- `/tools/keyboard-performance-test` URL, 화면, 측정 로직을 그대로 유지한다.
- `KeyboardPerformanceTester`, `KeyboardTesterNew`, 관련 사운드와 전역 CSS/헤더 등 간접 영향도 회귀 점검한다. 새 디자인은 신규 페이지 전용 레이아웃·스타일 범위에 적용한다.
- 기존 테스트의 평균 응답 값은 keydown~keyup 유지 시간이다. 이 값을 모델별 하드웨어 지연 데이터나 성능 순위로 재사용하지 않는다. 문제 수정은 별도 사용자 요청 때만 한다.
- 기존 유입 URL을 대규모 변경하지 않는다. 보존 페이지 메타데이터 변경도 이번 범위에서 제외한다.
- 근거 없는 평점, 가짜 후기, 미측정 수치, 임의 종합점수는 새 데이터베이스로 옮기지 않는다.

## 현재 확인한 사실

- Next.js App Router 기반. `src/app/page.tsx`는 소개 섹션들을 조합한다.
- `src/app/tools/page.tsx`, `src/lib/projects.ts` 등에 도구 소개가 나뉘어 있다. 신규 도구부터 공통 카탈로그를 사용하고 기존 성능 테스트 내부는 보존한다.
- `src/app/recommendations/page.tsx`는 제품·가격대·평점·후기 문구를 하드코딩한다. 해당 파일만으로 출처를 확인할 수 없는 값은 미검증 처리한다.
- `database-schema.sql`의 `keyboard_reviews`는 주관적 점수 중심이다. 모델·변형·측정환경·출처별 데이터 구조가 추가로 필요하다. SQL 파일이 운영 DB의 실제 상태라는 보장은 없다.
- 실제 `src/lib/projects.ts`는 SQL 선언의 tools/tool_screenshots와 달리 projects/screenshots를 조회한다. 현재 관리자 미들웨어·레이아웃은 세션 유무를 확인하므로 회원 제보를 추가할 때 이를 검토자 권한 확인으로 간주하지 않는다. 검토자 역할과 서버/DB 쓰기 권한을 별도로 검증한다.
- 운영 `/robots.txt`는 전체 Allow이며, 코드에는 robots.ts와 robots.txt가 함께 있다. 생성 경로를 하나로 정리한다. robots는 관리자 권한 제어 수단이 아니다.
- 2026-09-08 조회 시 사이트는 HTTPS www 주소에서 200 응답. 비-www 주소는 www로 308 이동한다. 사이트맵은 비-www URL을 사용하고 삭제된 `/contact`를 포함한다. 정상 응답이 현재 색인 상태나 과거 장애 원인을 증명하지는 않는다.
- 도메인 결제 지연 및 색인 감소는 사용자 제공 정보. 정확한 발생일·해제일·GSC 페이지별 색인 사유·평균순위는 아직 없다.

## 정보 구조

| 페이지 | 역할 | 연결 |
|---|---|---|
| `/` | 키보드 검색, 테스트 시작, 비교 진입 | 테스트 허브·카탈로그·방법론 |
| `/tools` | 측정 목적별 도구 허브 | 기존 성능 테스트, 신규 입력/KPS/재입력 확인 도구 |
| `/keyboards` | 브랜드·배열·연결·센서·기능별 탐색 | 모델 상세·비교 |
| `/keyboards/[slug]` | 모델 및 변형별 스펙·측정·출처 | 비교·측정법·관련 도구·제보 |
| `/compare` | 2~4개 제품 선택 비교 | 각 모델 상세·출처 |
| `/compare/[pair]` | 검토된 두 제품 비교 콘텐츠 | 모델 상세·기능 가이드 |
| `/guides/[slug]` | 검색 질문에 답하는 설명 | 적합한 도구·해당 기능 제품 |
| `/methodology` | 측정 가능한 것과 불가능한 것, 기준 버전 | 지표별 상세 설명 |
| `/contribute` | 스펙 수정·측정 결과 제보 | 제품 상세·검토 정책 |

후보 도구 경로: `/tools/keyboard-input-test`, `/tools/kps-test`, `/tools/rapid-trigger-test`. 마지막 도구는 키 눌림·해제·재입력 관찰 도구이며 래피드 트리거 지원 여부나 mm 감도의 자동 인증을 주장하지 않는다. 기존 사운드·사람 반응 테스트 URL은 유지하고 허브에서 목적을 분명히 설명한다.

내부 연결 규칙:
- 모든 공개 상세 페이지는 허브에서 일반 HTML 링크로 접근할 수 있어야 한다.
- 제품 상세 → 비교하기, 관련 측정법, 관련 테스트, 출처, 정정 제보를 제공한다.
- 가이드 → 답변에 필요한 도구와 실제 근거가 있는 제품으로 연결한다.
- 비교 결과 → 수치의 원문·측정환경·각 제품 상세로 연결한다.
- 보존 테스트로 들어가는 링크는 추가할 수 있으나 그 페이지의 나가는 링크를 위해 내부를 수정하지 않는다.
- 검색용으로 모든 제품 쌍·필터 조합을 자동 발행하지 않는다. 임시 비교는 공유 가능한 클라이언트 상태, 검색용 비교는 편집 검토된 안정 URL로 분리한다.

## 팩트 중심 성능 데이터

제품 하나에 점수 하나를 저장하는 방식 대신 개별 주장과 측정의 근거를 보존한다.

| 데이터 | 필수 속성 |
|---|---|
| 모델/변형 | 브랜드, 모델, 별칭, 배열, 지역판, 스위치, 하드웨어 리비전 |
| 공식 스펙 | 값·단위, 연결 모드, 원문 URL, 발행 주체, 확인일, 적용 변형 |
| 실측 | 지표, 값/분포, 단위, 표본 수, 방법론 버전, 장비, 펌웨어, 설정, 연결 모드, OS/환경, 측정일, 원본 근거 |
| 출처 | 유형, 원문 링크, 작성자/기관, 출처 날짜, 확인일, 이용 가능 범위 |
| 제보/검토 | 제출자, 대상 필드, 기존/제안 값, 증거, 상태, 검토자, 사유, 변경 이력 |

공개 표시는 `제조사 스펙`, `외부 실측`, `사이트 자체 실측`, `사용자 제출·미검토`, `사용자 제출·근거 검토`로 구분한다. 검토가 곧 독립 재측정은 아님을 표시한다.

성능표 후보 열:
- 제품/변형, 연결 모드, 공식 폴링레이트, 실측 입력 지연, RT 지원, 작동점 범위, 동시입력, 펌웨어, 측정법, 출처 확인일.
- 공식 8,000Hz를 실측 0.125ms 입력 지연으로 환산하지 않는다.
- 동일 테스트 정의·버전·연결·조건을 충족하는 데이터만 순위 비교한다. 조건이 다르면 나란히 보여도 순위는 매기지 않는다.
- 결측은 `미측정`/`미확인`으로 표시하고 0으로 처리하지 않는다. RT 미지원과 미확인을 구분한다.
- KPS와 사람 반응속도는 개인·환경 결과로 취급하며 키보드 모델 성능 순위에 넣지 않는다.
- 출처 충돌은 양쪽 근거와 적용 환경을 보존한다. 가장 작은 숫자나 최신 숫자로 자동 덮어쓰지 않는다.
- 가격은 통화·판매처·확인일을 함께 표시한다. 별점·인용 후기는 원문과 집계 조건이 확인된 경우에만 사용한다.
- 외부 리뷰 전문/이미지/데이터셋의 무단 복제를 전제로 하지 않는다. 링크·허용된 사실 인용과 자체 정리를 기본으로 한다.

새 저장 계층은 모델, 변형, sources, claims, measurements, submissions, revisions 개념으로 분리한다. 기존 DB·인증을 재사용할 수 있는지는 구현 전 실제 스키마·권한 확인으로 결정하며 리뷰 테이블을 바로 변형하지 않는다.

## 마니아 참여 흐름

잠정 추천은 로그인한 사용자의 근거 첨부 제보 → 운영자 검토 → 공개다. 사용자는 아직 참여 방식 질문에 답하지 않았다.

- 공식 스펙 정정, 펌웨어별 결과, 측정 기록, 출처 추가를 제출할 수 있다.
- 브라우저에서는 정확한 모델을 자동 확인할 수 없으므로 모델·변형 선택은 자기 신고로 표시한다.
- 증거 부족, 조건 불일치, 중복 제출을 구분해 보류/반려 사유를 남긴다.
- 같은 참가자의 반복 결과가 모델 표본 수를 과장하지 않도록 세션 수와 참가자 수를 구분한다.
- 서버에서 권한과 입력 형식을 검증한다. 공개 데이터 쓰기는 검토자만 허용한다. 업로드는 파일 종류·크기 제한, 비공개 검토, 공개 전 개인 정보 확인을 거친다.
- 운영자가 출처를 직접 등록하는 흐름도 지원한다. 인기 투표는 성능 수치와 분리한다.

## 디자인 방향

dark.design 실제 갤러리 화면에서 확인한 두 사례를 참고한다.

1. Electronic Materials Office: 큰 키보드 제품 이미지, 차콜 배경, 절제된 주황 포인트. 홈과 제품 상세에 적용.
   https://www.dark.design/site/electronic-materials-office
2. Fey: 어두운 다층 패널, 수치·차트의 차분한 배치. 비교표와 측정 결과에 적용.
   https://www.dark.design/site/fey

권장 방향은 ‘키보드 연구실’. 차콜 바탕, 밝은 회색 본문, 주요 동작에 주황 포인트, 수치에는 자릿수 폭이 일정한 글꼴을 사용한다. 정확한 색/여백 토큰은 구현 전 별도 시안에서 확정한다. 참고 사이트의 로고·이미지·문구는 복제하지 않는다.

- 홈 첫 화면: ‘내 키보드를 테스트하고, 근거로 비교하세요’ + 테스트 시작/키보드 비교 + 실제 제품 사진.
- 비교 화면: 고정 제품 머리글, 차이만 보기, 동일 조건 필터, 출처 펼치기, 단위와 측정일을 숫자 옆에 표시.
- 모바일: 두 제품 비교를 기본으로 하며 항목명과 선택 제품을 잃지 않는 구조. 3~4개 비교는 명시적 가로 스크롤 지원.
- 상태는 색뿐 아니라 텍스트로도 표시. 키보드 포커스, 접근 가능한 표, 축소 모션을 지원한다.
- 차트의 모든 중요한 결과는 HTML 텍스트·표로도 제공한다. 큰 배경 영상·과도한 광원 효과는 사용하지 않는다.
- 신규 페이지 스타일이 기존 성능 테스트에 번지지 않도록 레이아웃과 CSS 범위를 분리한다.

## SEO 복구와 AEO

복구를 재디자인보다 먼저 수행한다. 새 주소로 대규모 이전해 복구를 시도하지 않는다.

1. 도메인 자동 갱신·결제 알림·DNS/TLS 만료와 주요 URL 가용성을 운영 체크리스트에 둔다. 지금 결제 설정을 변경하거나 자동 모니터를 생성하지 않는다.
2. GSC의 장애 전후 날짜, 페이지 색인 사유, 크롤링 통계, URL 검사, Google 선택 canonical을 확인한다. 결제 지연을 유일한 원인으로 가정하지 않는다.
3. 현재 최종 호스트인 `https://www.withanalog.com`으로 신규 페이지·사이트맵·리디렉션 신호를 통일하는 방향을 우선 검토한다. 보존 테스트 내부 메타데이터는 손대지 않는다.
4. 사이트맵에는 정상 공개 canonical 페이지만 넣고 실제 수정일을 사용한다. `/contact`를 제거하고 공개 중인 누락 페이지를 검토한다.
5. robots 단일화, 의도치 않은 noindex/리디렉션 루프/soft 404/빈 HTML을 확인한다. 관리자 경로는 인증과 별도 색인 정책으로 보호한다.
6. 새 페이지별 고유 title·description·H1·canonical을 제공한다. 제품 스펙과 출처는 초기 서버 HTML에서 읽을 수 있게 한다.
7. 복구 후 GSC 사이트맵 재제출과 주요 URL 재크롤링 요청을 수행한다. 권한이 없으면 외부 의존성으로 명시하고 성공으로 기록하지 않는다.

검색어 그룹: 입력/인식·동시입력, KPS/CPS·연타, RT 재입력 확인, 지연/반응속도 설명, 사운드, 모델별 비교. 띄어쓰기/오타마다 페이지를 만들지 않는다.

AEO는 답변의 인용 가능성을 높이는 콘텐츠 구조로 접근한다.
- 질문에 대한 짧은 답 → 정의 → 조건별 성능표 → 측정 한계 → 출처 → 관련 테스트 순서.
- 모델 별칭·변형·단위·수정일을 일관되게 표기하고 작성/검토 주체를 공개한다.
- 페이지 성격에 맞는 BreadcrumbList, Product, Article 등을 검토하되 화면에 없는 값·평점·가격을 마크업하지 않는다.
- Google AI 검색에 특별한 AI 파일이나 전용 schema가 필수라는 주장은 하지 않는다. 색인과 스니펫 노출 자격, 텍스트 접근성, 내부 링크가 기본이다.
- FAQ 콘텐츠는 사용자의 질문에 답하기 위해 작성한다. 리치 결과나 AI 인용을 보장하지 않는다.
- 임시 검색/필터/비교 조합은 색인 대상에 넣지 않고 안정적인 편집 페이지에 집중한다. robots 차단과 noindex를 혼용해 noindex 확인을 막지 않도록 설계한다.

| 0 | 보존 페이지 기준선 및 GSC 현황 확보 | URL/파일 목록, 현재 화면·동작 기록, GSC 확인 가능한 항목과 미확인 항목 구분 |
| 1 | 기술 SEO·사이트맵·대표 주소 정리 | 공개 URL 200, 올바른 301/308, canonical 정합성, 삭제 URL 제외, 보존 페이지 회귀 통과 |
| 2 | 데이터 사전·출처/변형/측정 조건 및 검토 모델 | 서로 다른 펌웨어/연결 조건 분리, 출처 누락 발행 차단, 결측 처리 검증 |
| 3 | 홈·목록·상세·비교 디자인 및 구현 | 실제 근거 있는 표본 데이터로 데스크톱/모바일 탐색·비교·출처 확인 성공 |
| 4 | 도구 허브·가이드·신규 도구 연결 | 보존 테스트 그대로 유지, 신규 도구 정의 검증, 고립 페이지 없음 |
| 5 | 참여·검토·수정 이력 | 제보→보류/승인→공개, 일반 사용자 승인 불가, 개인정보 비공개 확인 |
| 6 | 검색·사용성·운영 검증 | 페이지별 HTML/메타/구조화 데이터, 링크 크롤링, 오류/빈 상태, 핵심 전환 기록 |

기능별 검증에는 제품 2~4개 선택/교체, 없는 모델, 결측, 서로 다른 측정법, 출처 충돌, 권한 없는 수정 시도, 모바일 표 탐색을 포함한다. 신규 측정 도구는 반복 키 입력·포커스 이탈·시작/중지·백그라운드 탭 처리·저장값 검증을 한다. 기존 성능 테스트의 파일 변경 여부와 실제 동작을 배포 전 확인한다.

콘텐츠 착수 목록: 브라우저 측정 한계, KPS와 CPS, 사람 반응시간과 키보드 지연 차이, RT 확인 방법, 동시입력 확인, 폴링레이트와 지연의 차이. 모델 목록은 원문 근거를 확보한 제품부터 공개하며 목표 개수를 채우려고 수치를 생성하지 않는다.

평가 지표: 정상 색인 가능 URL 비율, GSC 색인 페이지 변화, 검색어 그룹별 노출/CTR/평균순위, 테스트 시작·완료, 제품 비교 실행, 출처 열람, 근거 충족 데이터 비율, 제보 처리시간. 순위/클릭 목표는 장애 전 기준선과 검색 기간을 확인한 뒤 수립한다. AI 유입은 식별 가능한 referral을 측정하며 전체 인용을 측정했다고 주장하지 않는다.

## 구현 전에 확인할 운영 사항

참여 공개 방식(현재 질문 중), 실제 측정 장비/데이터 확보 가능 여부, 초기 대상 모델, GSC 접근과 장애 날짜. 이 항목들은 전체 계획 수립을 막지 않지만 실제 데이터 공개와 색인 복구 확인의 선행 조건이다. 현재는 어떠한 실측 장비나 외부 데이터 사용권도 확보됐다고 가정하지 않는다.
